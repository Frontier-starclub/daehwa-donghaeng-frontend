# 미결정 사항 (Blocker)

화면설계서 v2.1 Decision Log에서 "팀 확정 필요"로 남은 항목들.
**A/B/C가 안 풀리면 해당 화면은 코드를 짤 수 없다.** 우선 처리 대상이다.

---

## Blocker A — 직접 입력(OCR-07) 항목 범위

- **담당**: 이석윤 · **기한**: 9/8 · **상태**: 제안
- **문제**: 촬영이 불가능하거나 인식에 실패했을 때 사용자가 직접 입력하는 경로가 항상
  열려 있어야 한다(플로우차트 FC-01). 이때 무엇까지 받을 것인가.

**제안**: **약 이름 + 1일 복용 횟수만.**

근거 — 백엔드 `MedicationDraft`에서 `name`만 필수이고 `ingredient_name`,
`ingredient_code`, `item_seq`, `dose_frequency_per_day`가 전부 nullable이다.
성분코드를 고령자에게 입력하라고 할 수 없고, 그럴 필요도 없다.
**스키마 변경 없이 끝난다.**

부작용: 직접 입력한 약은 `item_seq`가 없어 DUR 조회가 제한된다.
→ Blocker B의 이름 매핑(`/v1/drugs/resolve`)으로 보완하고, 매핑에 실패하면
DUR 화면에서 "확인 불가"로 표시한다.

## Blocker B — 약 이름 → 코드 매핑

- **담당**: 정진수 · **기한**: 9/9 · **상태**: 스파이크 필요 (9/8)
- **문제**: OCR은 약 이름만 읽는다. DUR API는 품목기준코드 등 식별자를 요구한다.
  그 사이를 무엇으로 메울 것인가. **MVP에서 모델링 여지가 있는 유일한 지점이다.**

**9/8 스파이크에서 확인할 것**

1. [DUR 품목정보 API](https://www.data.go.kr/data/15059486/openapi.do)의
   `getUsjntTabooInfoList03` 등이 **실제로 요구하는 요청 파라미터**
   — 품목기준코드인가, 제품명으로도 되는가
2. 제품명으로 조회가 된다면 **매핑 자체가 불필요**해질 수 있다 → 먼저 확인한다
3. 매핑이 필요하다면 [낱알식별](https://www.data.go.kr/data/15057639/openapi.do) /
   [e약은요](https://www.data.go.kr/data/15075057/openapi.do) 중 커버리지가 넓은 쪽

**접근 순서** — 단순한 것부터. ③은 ①②로 부족하다는 측정이 나온 뒤에만 간다.

1. 정규화(공백·괄호·용량 표기 제거) 후 완전일치
2. 부분일치
3. 유사도 매칭

**실패 처리**: 매칭 실패는 오류가 아니다. `item_seq: null`, `confidence: 0.0`으로
돌려주고 DUR 단계에서 "확인 불가"로 처리한다. **잘못된 매핑보다 확인 불가가 안전하다** —
없는 경고를 만들어내거나 있는 경고를 놓치는 쪽이 훨씬 위험하다.

관련 저장 위치: `medications.ingredient_code`, `medications.item_seq` 컬럼이 이미 있다.

## Blocker C — 기존 복용약 확보

- **담당**: 이석윤 · **기한**: 9/8 · **상태**: 제안
- **문제**: 신규 약과 비교할 "기존 복용약"을 어디서 가져오는가.
  후보: 앱 등록 이력 자동 사용 / 최초 1회 직접 입력 / 새 약봉투 내부만 비교

**제안**: **앱 등록 이력 자동 사용. 추가 개발 없음.**

근거 — 백엔드 `POST /dur-checks`가 이미 사용자의 활성 약(`status = "active"`) 전체를
조회해 스냅샷으로 넘긴다(`apps/backend/app/api/medications.py`). 앱이 아무것도 보내지
않아도 기존 복용약 전체가 비교 대상에 들어간다.

한계: 앱을 처음 쓰는 사용자는 기존 복용약이 비어 있어 첫 등록 때 상호작용 확인이
의미가 없다. 파일럿 안내 문구로 보완한다("드시던 약도 함께 등록해 주세요").

화면설계서가 `MVP: MUST` 35화면을 제안하되 "팀이 확정하지 않았다"고 남겨둔 항목.

**제안**: 구현은 35화면 전부. **통합 테스트와 파일럿 시나리오만 Core 22화면으로 한정.**

사항, 실기기 확인, 코드 응집도다. 따라서 줄여야 할 것은 구현 범위가 아니라 **검증 범위**다.
