## 1. MVP 컷라인 (화면설계서 Decision Log S-3)

화면설계서가 `MVP: MUST` 35화면을 제안하되 "팀이 확정하지 않았다"고 남겨둔 항목입니다.

**제안: 구현은 35화면 전부. 통합 테스트와 파일럿 시나리오만 Core 22화면으로 한정.**

에이전트 코딩을 쓰면 화면 코드 생성이 병목이 아닙니다. 화면설계서가 Screen ID별로
목적·표시정보·버튼·다음 화면·필요 데이터·오류 예외까지 명세해 두어서 그대로 코드가 나옵니다.

실제 병목은 다른 데 있습니다.

- 35화면을 에뮬레이터에서 눌러보고 고치는 왕복 (사람이 해야 함)
- Blocker A/B/C가 안 풀리면 OCR-07·DUR 전 화면은 코드를 못 짬
- STT/TTS, 카메라 권한, 고령자 폰트는 실기기에서만 드러남

그래서 줄여야 할 것은 구현 범위가 아니라 **검증 범위**입니다.

## 2. 보호자(Caregiver) 연동 M3 이월

회의록 Phase1은 *복약 캘린더 + 보호자 연동*입니다. 현재 백엔드에는 복약 캘린더는
완성되어 있으나 보호자 쪽은 `consents.caregiver_share_allowed` 플래그만 있고
Caregiver 모델·API가 없습니다.

이는 회의록 결정사항 1("8월은 MVP 2단계 OCR+DUR에 집중")과 안건1 결론("분석은 제외")에
따라 **팀이 의도적으로 뒤로 민 것**으로 이해하고 있습니다. 누락이 아닙니다.

이 이해가 맞다면 M3(12월) 스코프로 확정하고, FE에서도 REPORT-01/02, INSIGHT-01/02를
같은 시점으로 잡겠습니다.

- [ ] 맞습니다 — M3로 확정
- [ ] 아닙니다 — 9월 내 필요 (이 경우 일정 재조정이 필요합니다)

## 3. 프로젝트 목표 정렬 — 정식 배포 대 시연

회의록 성공기준은 다음과 같습니다.

- MVP v1.0 앱 완성 및 **Google Play 등록**
- **실사용자 파일럿 10명 이상** 운영 및 복약 확인율·만족도 측정
- 복지관 등 기관 1곳 이상 파일럿 제안

한편 FE 쪽에서는 "정식 배포는 미정이고 창업 멘토 시연 중심 아닌가"라는 이야기가 있었습니다.
**두 전제는 개발 방향이 다릅니다.**

| | 정식 배포 | 시연 중심 |
| --- | --- | --- |
| 앱 배포 | Play 등록, 서명, 개인정보처리방침 | 에뮬레이터·실기기 직접 시연 |
| 파일럿 | 실사용자 10명에게 설치 | 팀 내부 시연 |

| 9월 이후 작업량 | 큼 | 작음 |

프레임워크(Flutter)나 아키텍처는 **어느 쪽이든 바뀌지 않습니다.** 달라지는 것은
Play 등록 준비와 파일럿 운영에 드는 시간입니다.

- [ ] 회의록대로 — Play 등록 + 파일럿 10명 유지

## 참고 — 확정된 것 (확인 불필요)

FE·AI 파트에서 이미 정하고 진행 중인 사항입니다. 기록 목적으로만 남깁니다.

- 저장소 2개 운영 (백엔드 / 앱·AI). 근거는 `docs/decisions/2026-09-06-repo-split.md`
- 앱 프레임워크는 Flutter 유지
- OCR은 Claude API로 시작하고 평가셋 20건으로 검증. 모델 변경 시 별도 확인 요청
- Blocker A(직접 입력 범위), C(기존 복용약)는 백엔드 스키마 변경 없이 처리 가능
- 모든 DUR 화면에 "의사·약사 상담을 권고합니다" 문구 유지 (회의록 결정사항 2).
  백엔드가 내려주는 값을 렌더링하며 앱에서 하드코딩하지 않습니다
